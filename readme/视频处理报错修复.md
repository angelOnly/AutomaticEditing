可以，而且我同意：**不应该物理拼接多个源视频。**

当前流程不是把 30 分钟视频整段丢给大模型。它后面会按 `chunk_seconds` 拆，比如 60 秒一段，再每段抽几帧给视觉模型，ASR 也是先抽音频再分段识别。所以“大模型一次处理不了 30 分钟”这一点目前靠 chunk 机制缓解了。

但问题在于：**为了得到连续时间轴而先生成 `source_multi.mp4`，这个设计本身不优雅，也脆弱。**

为什么当初这么做？主要是为了复用单视频 pipeline：

- 单视频 pipeline 只认一个 `source_video`
- metadata / audio_extract / frame_extract / chunk_build / asr / vision 都默认围绕一个输入文件跑
- 多源拼成一个代理视频后，后续步骤不用大改
- 再用 `source_manifest.json` 记录每个源视频在虚拟时间轴里的起止位置

这个是工程捷径，不是最佳设计。现在遇到的坏处也很明显：

- 多一次长视频转码/拼接，耗时、占空间、容易失败
- 并发公共缓存时容易写坏中间文件
- “拼接原片”会误导用户，以为这是原始素材
- 真实源视频明明正常，中间代理视频坏了，后续就全错
- 视频越多越长，代理文件越大，越不稳定

正确方案应该是：**多源原生处理，逻辑拼接，不物理拼接。**

也就是保留一个“虚拟总时间轴”，但不要生成 `source_multi.mp4`。

流程改成这样：

1. `source_prepare`
   只生成 `source_manifest.json`，记录每个视频：
   `source_id`、`original_path`、`duration`、`virtual_start`、`virtual_end`。

2. `metadata`
   对每个源视频单独 ffprobe。

3. `audio_extract`
   每个源视频单独抽音频，得到：
   `audio/source_001.wav`、`audio/source_002.wav`。

4. `frame_extract`
   每个源视频单独抽帧，帧记录同时包含：
   `source_id`、`local_time`、`virtual_time`。

5. `chunk_build`
   不按一个大视频切 chunk，而是生成多源 chunk：
   `source_001/chunk_0001`、`source_002/chunk_0001`。
   每个 chunk 也带虚拟时间：
   `virtual_start = source_virtual_start + local_start`。

6. `asr`
   每个源视频单独 ASR，ASR 结果统一加上 `source_id` 和虚拟时间偏移。

7. `vision`
   每个源视频每个 chunk 单独视觉理解，模型仍然只看 60 秒附近的文本和几张帧图，不会吃整条长视频。

8. `timeline`
   把多个源的 ASR + vision 结果合并成一个逻辑时间轴。

9. 后续大模型
   读的是压缩后的多源 timeline / digest，不读物理拼接视频。

10. 渲染
   高光重组时直接从原始源视频裁切。只有最终导出片段时才转码统一格式。

所以答案是：**能多个视频直接处理，而且应该这么做。**

我建议后续不要再修补 `source_multi.mp4` 这条路线了，最多短期加校验止血。真正优化应该是把多源从“物理拼接代理视频”改成“manifest 驱动的虚拟时间轴”。这样既保留连续叙事能力，也不会让坏的中间拼接文件拖垮整个任务。


对，这个要从“物理拼接多源”改成“虚拟时间轴多源”。我建议这样改。

**总体目标**
保留现有后半段 Agent 链路，但前半段不再生成 `source_multi.mp4`。

新的多源链路：

```text
source_request
→ source_manifest 虚拟时间轴
→ 每个源视频单独 metadata/audio/frame/chunk/asr/vision
→ 合并成统一 timeline / timeline_digest
→ 后续 Agent 继续使用 timeline_digest
→ 渲染时从原始源视频裁切
```
