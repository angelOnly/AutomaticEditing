下面这版是在原技术方案基础上的优化，重点解决你现在提出的需求：

> **每个步骤的执行结果都要保存下来；如果某一步不满意，可以只重跑这一环节，而不是每次从头开始。尤其是大模型解析视频、大模型分析结果、高光识别、文案生成等步骤，都要支持缓存、版本管理、局部重生成。**

这意味着系统不能设计成一个简单的：

```text
input.mp4 → run_pipeline.py → final.mp4
```

而应该设计成一个 **可断点续跑、可缓存、可回溯、可局部重生成的新闻视频智能拆条流水线系统**。

# 一、核心优化目标

## 1. 每个步骤结果都要落盘

系统中的每一步都要保存中间产物，包括：

```text
视频元信息
抽帧结果
ASR 结果
视频分段结果
大模型逐段解析结果
统一时间轴
新闻理解结果
高光片段结果
短视频规划结果
剪辑脚本
解说文案
配音音频
字幕文件
自动剪辑方案
粗剪视频
风险审核结果
```

这样后续才能做到：

```text
不满意 ASR → 只重跑 ASR 及其后续依赖
不满意某段视频理解 → 只重跑该 chunk 的多模态解析
不满意高光识别 → 只重跑高光识别
不满意文案 → 只重跑文案 Agent
不满意配音 → 只重跑 OmniVoice
不满意剪辑 → 只重跑剪辑导出
```

---

## 2. 每个步骤都要有输入、输出和依赖关系

不能只是顺序执行，而要设计成 DAG 流程。

也就是：

```text
某个步骤是否需要重跑，取决于它的上游输入有没有变化
```

例如：

```text
ASR 没变
抽帧没变
多模态解析没变
merged_timeline 没变

那么高光识别可以直接复用已有输入，只重跑 highlight_agent
```

---

## 3. 每个大模型调用结果都要保存原始响应

尤其是多模态模型解析视频，必须保存：

```text
模型输入
模型输出
原始响应
解析后的 JSON
使用的 Prompt
使用的模型名称
模型参数
调用时间
对应视频时间段
失败信息
人工修改记录
```

这样后面才能知道：

```text
模型当时看了哪些帧？
给了什么 ASR 文本？
用了哪个 Prompt？
为什么输出这个判断？
如果要重跑，是重跑同样输入，还是改 Prompt 后重跑？
```

# 六、缓存与重跑机制

## 6.1 默认逻辑：能复用就复用

每个步骤执行前先检查：

```text
1. 当前步骤是否已有成功输出
2. 输入文件是否没有变化
3. Prompt 版本是否没有变化
4. 模型配置是否没有变化
5. 用户是否强制重跑
```

如果都满足，就直接复用结果。

---

## 6.2 判断是否需要重跑

用 `input_hash` 判断。

每个步骤的输入包括：

```text
上游 JSON 文件
Prompt 文本
模型名称
模型参数
用户配置
视频片段时间范围
关键帧路径列表
ASR 文本
```

把这些内容计算 hash。

如果 hash 没变：

```text
直接复用缓存
```

如果 hash 变了：

```text
生成新版本 v2
```

---

## 6.3 重跑模式

建议支持 4 种重跑模式。

### 模式 1：复用缓存

```bash
python run_pipeline.py input.mp4 --resume
```

含义：

```text
已有成功结果就复用，只跑缺失步骤
```

---

### 模式 2：强制重跑某一步

```bash
python run_pipeline.py input.mp4 --rerun highlight_detection
```

含义：

```text
只重新生成高光识别结果
```

如果下游依赖它，可以选择是否继续重跑下游。

---

### 模式 3：重跑某一步及其下游

```bash
python run_pipeline.py input.mp4 --rerun-from highlight_detection
```

含义：

```text
重新跑高光识别
并重新跑短视频规划、剪辑脚本、文案、审核、剪辑
```

适合高光片段不满意时使用。

---

### 模式 4：只重跑某个视频 chunk 的多模态解析

```bash
python run_pipeline.py input.mp4 --rerun vision --chunk chunk_0007
```

含义：

```text
只重新调用大模型分析第 7 个视频分段
其他 chunk 结果复用
```

这是你现在特别需要的能力。

---

# 七、重点优化：大模型解析视频结果如何保存

大模型解析视频是最贵、最慢、最容易不稳定的一步，所以必须设计得特别细。

## 7.1 视频不要整体丢给大模型

建议拆成 chunk：

```text
每 30 秒 / 60 秒一个 chunk
或按镜头切分成 chunk
```

每个 chunk 单独调用多模态模型。

这样好处是：

```text
某一段解析不好，只重跑这一段
不会因为一段失败导致整条视频失败
可以并发调用
可以单独人工修正某一段
可以对重点段落加密抽帧重新分析
```

---

## 7.2 每个 chunk 保存完整输入

例如：

```text
vision/v1/chunk_0007/input.json
```

内容：

```json
{
  "task_id": "task_20260525_0001",
  "chunk_id": "chunk_0007",
  "time_range": {
    "start": "00:06:00",
    "end": "00:07:00"
  },
  "frames": [
    "preprocess/frames/frame_000072.jpg",
    "preprocess/frames/frame_000078.jpg",
    "preprocess/frames/frame_000084.jpg"
  ],
  "asr_segments": [
    {
      "start": "00:06:02.100",
      "end": "00:06:08.200",
      "text": "记者在现场介绍，目前……"
    }
  ],
  "prompt_version": "vision_chunk_v1.3",
  "model": "qwen-vl",
  "model_params": {
    "temperature": 0.1,
    "response_format": "json"
  }
}
```

---

## 7.3 每个 chunk 保存 Prompt

```text
vision/v1/chunk_0007/prompt.txt
```

保存完整 Prompt，而不是只保存版本号。

因为后续排查时要知道模型到底看到了什么指令。

---

## 7.4 每个 chunk 保存模型原始响应

```text
vision/v1/chunk_0007/raw_response.json
```

里面保存完整原始响应。

示例：

```json
{
  "model": "qwen-vl",
  "created_at": "2026-05-25T12:10:00",
  "raw_text": "{...模型返回的原始内容...}",
  "usage": {
    "input_tokens": 5312,
    "output_tokens": 832
  },
  "finish_reason": "stop"
}
```

---

## 7.5 每个 chunk 保存解析后的标准 JSON

```text
vision/v1/chunk_0007/parsed_result.json
```

示例：

```json
{
  "chunk_id": "chunk_0007",
  "time_range": "00:06:00-00:07:00",
  "scene_type": "记者现场连线",
  "visual_summary": "记者在户外进行现场连线，背景为城市街道。",
  "screen_text": [
    "凤凰卫视",
    "现场连线",
    "华盛顿"
  ],
  "visible_people": [
    {
      "role": "记者",
      "confidence": "medium"
    }
  ],
  "is_live_scene": true,
  "is_archive_footage": false,
  "visual_value_score": 8,
  "hook_score": 7,
  "risk_tags": [],
  "asr_visual_consistency": "consistent",
  "notes": "该片段具备现场感，适合作为候选高光。"
}
```

---

## 7.6 每个 chunk 保存人工修订结果

如果编辑觉得大模型解析不准，可以人工改。

不要直接覆盖模型结果，而是新增：

```text
vision/v1/chunk_0007/manual_override.json
```

示例：

```json
{
  "manual_edited": true,
  "editor": "news_editor_01",
  "updated_at": "2026-05-25T13:00:00",
  "fields_overridden": {
    "scene_type": "资料画面",
    "is_live_scene": false,
    "is_archive_footage": true,
    "notes": "画面左上角有资料字样，不能按现场画面处理。"
  }
}
```

最终时间轴融合时使用：

```text
manual_override > parsed_result
```

也就是人工修订优先。

# 八、大模型结果版本管理

## 8.1 为什么要版本管理

大模型分析经常会因为这些变化导致结果不同：

```text
Prompt 修改
模型更换
temperature 修改
抽帧策略修改
ASR 结果修改
chunk 分段方式修改
人工补充背景信息
```

所以不能只保存一个 `visual_analysis.json`。

应该保存：

```text
vision/v1/
vision/v2/
vision/v3/
```

---

## 8.2 每个版本表示一次完整生成

例如：

```text
vision/v1：第一次用 Qwen 按 60 秒 chunk 解析
vision/v2：修改 Prompt 后重跑 chunk_0007
vision/v3：切换豆包多模态重跑全部 chunk
```

manifest 里记录当前使用哪个版本：

```json
{
  "current_versions": {
    "vision": "v2"
  }
}
```

---

## 8.3 局部重跑时如何生成版本

这里有两种方案。

### 方案 A：重跑 chunk 后生成新的 vision 版本

比如只重跑 `chunk_0007`：

```text
vision/v1/
  chunk_0001
  chunk_0002
  chunk_0007 旧结果

vision/v2/
  chunk_0001 复用 v1
  chunk_0002 复用 v1
  chunk_0007 新结果
```

优点：

```text
版本清晰，整套 visual_analysis.json 可回溯
```

缺点：

```text
占用空间稍多
```

我更推荐这个方案。

---

### 方案 B：只替换 chunk 结果

不推荐作为默认方式，因为不利于回溯。

最终需要生成：


结构：

```json
{
  "version": "v1",
  "chunks": [
    {
      "chunk_id": "chunk_0001",
```

# 十、局部重生成的依赖关系

下面是关键步骤的依赖关系。

```text
video_metadata
  ↓
audio_extract
  ↓
FunASR
  ↓
merged_timeline
  ↓
video_understanding
  ↓
highlight_detection
  ↓
short_video_planning
  ↓
editing_script
  ↓
voiceover_script
  ↓
OmniVoice
  ↓
cut_plan
  ↓
render
```

多模态部分：

```text
frames + chunks + ASR
  ↓
vision_chunk_analysis
  ↓
visual_analysis
  ↓
merged_timeline
```

所以：

## 10.1 如果只改解说文案

只需要重跑：

```text
voiceover_script
↓
OmniVoice
↓
render
```

不需要重跑：

```text
ASR
多模态分析
高光识别
短视频规划
```

---

## 10.2 如果只改高光识别 Prompt

重跑：

```text
highlight_detection
↓
short_video_planning
↓
editing_script
↓
voiceover_script
↓
risk_review
↓
OmniVoice
↓
render
```

不需要重跑：

```text
ASR
多模态解析
merged_timeline
video_understanding
```

---

## 10.3 如果只对某个 chunk 的视频理解不满意

重跑：

```text
vision_chunk_analysis: chunk_0007
↓
visual_analysis 合并
↓
merged_timeline
↓
video_understanding
↓
highlight_detection
↓
short_video_planning
↓
editing_script
↓
voiceover_script
↓
risk_review
```

不需要重跑：

```text
视频预处理
抽帧
ASR
其他 chunk 的多模态解析
```

---

## 10.4 如果 ASR 不满意

重跑：

```text
FunASR
↓
chunks 里的 asr_text 更新
↓
vision_chunk_analysis 可选择是否重跑
↓
merged_timeline
↓
后续所有 Agent
```

这里要注意：

如果 ASR 文本变了，多模态 chunk 的输入也变了。

但可以提供两种选择：

```text
保守模式：ASR 变了，重跑所有 vision chunk
快速模式：ASR 变了，只重建 timeline，不重跑 vision
```

建议默认：

```text
ASR 大幅变化 → 重跑 vision
ASR 小幅修正 → 不重跑 vision，只重建 timeline
```

## 11.2 断点续跑

```text
已有结果直接复用，只跑缺失或失败步骤
```

# 十四、人工修改与重生成的关系

人工修改非常关键。

比如编辑手动改了某个高光片段时间码：

```json
{
  "clip_id": "C001",
  "start": "00:02:10",
  "end": "00:03:05"
}
```

这时候系统不应该重跑高光识别覆盖人工修改。

正确做法是：

```text
candidate_clips.json 原始模型结果保留
manual_candidate_clips.json 保存人工修改
后续 short_video_planning 使用人工修改后的结果
```

也就是说：

```text
模型结果层
↓
人工修订层
↓
最终采用层
```

建议每个关键步骤都保留三份：

```text
model_output.json
manual_override.json
final_output.json
```

例如：

```text
agents/highlight_detection/v1/
  model_output.json
  manual_override.json
  final_output.json
```

# 十六、推荐的 Step 编排方式

建议不要写死一个巨大函数，而是每个 Step 独立成类。

```python
class PipelineStep:
    name: str
    dependencies: list[str]

    def build_input(self, context):
        pass

    def compute_hash(self, input_data):
        pass

    def should_run(self, context, force=False):
        pass

    def run(self, input_data):
        pass

    def save_result(self, result):
        pass
```

每个步骤继承它：

```python
class ASRStep(PipelineStep):
    name = "asr"
    dependencies = ["audio_extract"]

class VisionChunkStep(PipelineStep):
    name = "vision_chunk_analysis"
    dependencies = ["frames", "chunks", "asr"]

class HighlightDetectionStep(PipelineStep):
    name = "highlight_detection"
    dependencies = ["merged_timeline", "video_understanding"]
```

这样才能实现：

```text
按步骤运行
按依赖运行
断点续跑
局部重跑
版本管理
```

# 十七、run_pipeline 的优化伪代码

```python
def run_pipeline(task_id, rerun_step=None, rerun_from=None, chunk_id=None, resume=True):
    context = load_task_context(task_id)
    manifest = load_manifest(task_id)

    steps = [
        MetadataStep(),
        AudioExtractStep(),
        FrameExtractStep(),
        ChunkBuildStep(),
        ASRStep(),
        VisionAnalysisStep(),
        TimelineBuildStep(),
        VideoUnderstandingAgentStep(),
        HighlightDetectionAgentStep(),
        ShortVideoPlanningAgentStep(),
        EditingScriptAgentStep(),
        VoiceoverScriptAgentStep(),
        RiskReviewAgentStep(),
        OmniVoiceStep(),
        SubtitleStep(),
        CutPlanStep(),
        RenderStep()
    ]

    selected_steps = resolve_steps(
        steps=steps,
        rerun_step=rerun_step,
        rerun_from=rerun_from
    )

    for step in selected_steps:
        if step.name == "vision_analysis" and chunk_id:
            step.run_chunk(context, chunk_id=chunk_id)
            continue

        input_data = step.build_input(context)
        input_hash = step.compute_hash(input_data)

        if resume and not step.should_run(manifest, input_hash):
            print(f"reuse cache: {step.name}")
            continue

        version = step.create_new_version(context)
        result = step.run(input_data)
        step.save_result(result, version=version)
        update_manifest(task_id, step.name, version, result)
```

# 十八、如何处理下游失效

如果上游改了，下游理论上都需要更新。

比如高光识别重跑后：

```text
short_video_planning
editing_script
voiceover_script
risk_review
cut_plan
render
```

都应该标记为：

```text
stale
```

而不是直接删除。

manifest 中可以记录：

```json
{
  "steps": {
    "short_video_planning": {
      "status": "stale",
      "reason": "upstream highlight_detection updated from v1 to v2"
    }
  }
}
```

这样用户可以选择：

```text
继续使用旧版本
或者基于新高光结果重跑下游
```
