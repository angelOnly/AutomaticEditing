# 提示词优化最终报告

## 一、最终结论

这次优化的核心不是“把提示词写得更长”，而是要重构职责：

> **大模型只做编辑判断，代码负责结构化补全。**

也就是说：

```text
大模型负责：
选哪些片段、怎么排序、讲述重点是什么、必须讲到哪些事实。

代码负责：
clip_id、source_id、start、end、duration、shot_id、short_video_id、reassembly_id、字幕对齐、时长计算、字段兼容。
```

以前很多 prompt 的问题是：
让模型输出了太多它不该输出、也不稳定输出的东西。

比如：

```text
时间码
时长
ID
source_id
各种分数
上下文范围
事件组
transition_after
excluded_clip_ids
ok/rewrite/missing
```

这些字段要么代码已知，要么下游没用，要么定义模糊，要么模型输出不可靠。

最终优化方向：

```text
1. 删除无效 prompt。
2. 删除公共大段策略。
3. 每个 prompt 只保留自己的职责规则。
4. 所有输出 schema 极简化。
5. 增加代码 materialize 层，把模型极简输出补成旧工程需要的完整结构。
```

# 三、为什么要删除这些 prompt

## 1. 删除 `VOICEOVER_QUALITY_CHECK_PROMPT`

这个 prompt 当前没有实际价值。

它输出：

```json
{
  "ok": 1,
  "rewrite": 0,
  "missing": []
}
```

但问题是：

```text
1. 不自动触发重写。
2. 不真正阻断 TTS。
3. 失败时容易默认通过。
4. 输出字段无法帮助后续剪辑。
5. 还会增加一次 LLM 调用成本。
```

所以应该直接删。

文案质量检查应该改成代码规则：

```text
1. narration_text 是否为空。
2. narration_segments 是否和 shot_id 对齐。
3. 是否出现营销号词汇。
4. 是否出现“记者某某报道”。
5. 单句是否过长。
6. narration_text 是否等于 segments 合并结果。
```

这比再跑一个 LLM 更稳定。

---

## 2. 删除 `CANDIDATE_REFINE_PROMPT`

原本它输出：

```json
{
  "k": 1,
  "u": "both",
  "i": 1,
  "c": 0,
  "g": "g1",
  "r": 1
}
```

问题很明显：

```text
k/u/i/c/g/r 字段不可读。
使用方向没有强下游逻辑。
是否需要上下文定义模糊。
事件组没有全局输入基础。
排序应该由最终成片规划决定。
```

它属于“看起来有用，实际制造噪音”的步骤。

候选筛选应该前移到：

```text
CONTENT_ANALYSIS_PROMPT
HIGHLIGHT_DETECTION_PROMPT
```

最终选择应该交给：

```text
SHORT_VIDEO_EDIT_PLAN_TEXT_PROMPT
HIGHLIGHT_REASSEMBLY_TEXT_PROMPT
```

所以可以删。

---

## 3. 删除 `MERGE_DECISION_PROMPT`

它是补救型 prompt。

原逻辑是：

```text
short_video_edit_plan 已经拆成多条后，
再让 merge_decision 判断要不要合并。
```

这不合理。

正确做法是：

```text
不要乱拆的规则前移到 SHORT_VIDEO_EDIT_PLAN_TEXT_PROMPT。
```

也就是：

```text
默认只做一条完整短视频。
只有明显不同新闻事件、不同强角度、不同人物阶段，才允许拆多条。
```

这样不需要后面再补救。

---

## 4. 删除旧版 prompt

这些删掉：

```text
SHORT_VIDEO_PLANNER_PROMPT
EDITING_DIRECTOR_PROMPT
VOICEOVER_PROMPT
RISK_REVIEW_PROMPT
HIGHLIGHT_REASSEMBLY_PROMPT
SHORT_VIDEO_EDIT_PLAN_PROMPT
```

原因：

```text
1. 当前主链没有实际使用。
2. 和 TEXT 版 prompt 职责重复。
3. 会造成维护混乱。
4. 规则散落两套，后续不知道改哪个。
```

其中 `VOICEOVER_PROMPT` 里的好规则不要丢，要合并进新版 `VOICEOVER_SCRIPT_TEXT_PROMPT`。

你补充的配音文案标准非常重要，尤其是：开头快速点题、短句、新闻口吻、不营销号、和 shot 对齐、适合字幕。这个应作为新版配音 prompt 的核心。

# 四、公共策略最终处理方案

## 1. `COMMON_JSON_OUTPUT_RULES`

删除。

原因：

```text
每个 prompt 都应该自己写输出要求。
公共 JSON 规则只是重复噪音。
```

每个 prompt 末尾统一写：

```text
输出要求：
1. 只输出 JSON。
2. 不要输出 Markdown。
3. 不要解释。
4. 严格使用指定字段。
5. 不要新增字段。
```

这样更直接。

---

## 2. `MULTI_SOURCE_BOUNDARY_POLICY`

保留，但不再作为泛用公共提示词。

它要变成：

```text
多源素材边界与跨源编排规则模块
```

只插入这两个 prompt：

```text
SHORT_VIDEO_EDIT_PLAN_TEXT_PROMPT
HIGHLIGHT_REASSEMBLY_TEXT_PROMPT
```

它的职责是：

```text
1. 判断不同 source_id 的 clip 能不能放进同一条视频。
2. 避免把不同源误认为同一现场连续镜头。
3. 避免从一个源的半句话切到另一个源的半句话。
4. 跨源组合必须有新闻逻辑。
5. 多条输出时避免重复使用同一个开头源。
```

它不要求模型额外输出字段。

也就是说，它只影响：

```text
clip_ids 的选择和排序。
```

不输出：

```text
source_id
start
end
duration
reason
split_reason
```

因为这些会让 schema 变复杂。

---

## 3. `SHORT_VIDEO_DURATION_POLICY`

删除公共块，但保留核心逻辑。

它应该拆成两部分。

### 放进 `SHORT_VIDEO_EDIT_PLAN_TEXT_PROMPT`

用于指导选片：

```text
你不输出目标时长。
你根据候选 clip 的 duration_seconds 选择合适数量的 clip。
每条视频所选 clip 总时长尽量落在 min/max 范围内。
不要为了凑时长选择低信息量片段。
```

### 放进 `VOICEOVER_SCRIPT_TEXT_PROMPT`

用于控制字数：

```text
输入会提供当前视频视觉总时长。
请按视觉总时长生成接近该时长的配音文案。
中文 TTS 可粗略按每秒 4-5 个汉字估算。
不要为了凑字数重复事实。
```

这比公共时长策略更有效。

---

## 4. `VISUAL_EVIDENCE_POLICY`

删除公共块。

原因：

```text
高光判断 prompt 里本来就应该有画面证据细则。
公共块太泛，不能直接改变模型决策。
```

拆进两个地方。

### 放进 `VISION_CHUNK_PROMPT`

```text
识别画面类型：
现场画面、人物讲话、主持人口播、资料画面、地图图表、空镜/B-roll。

只描述画面能确认的事实。
不要根据 ASR 推断画面没有出现的信息。
疑似资料画面必须标明。
```

### 放进 `CONTENT_ANALYSIS_PROMPT / HIGHLIGHT_DETECTION_PROMPT`

```text
优先选择画面能支撑新闻事实的片段。
纯主持人口播、重复空镜、无新增信息 B-roll，不应单独作为候选。
资料画面只能作为辅助，不得当成事件现场。
```

# 五、最终保留 prompt 设计

---

## 1. `ASR_DIGEST_PROMPT`

### 是否保留

保留。

### 职责

把 chunk 的原始 ASR 压缩成新闻事实摘要。

### 不做什么

```text
不选片。
不判断高光。
不生成标题。
不评论。
不补充背景。
```

### 输出

```json
{
  "speech": ""
}
```

### 优化方向

提示词要强调新闻事实保留：

```text
必须保留：
人物、机构、地点、时间、动作、结果、数字、态度、否定词、条件限制、引语边界。

删除：
口水词、重复句、无意义寒暄、语气词。
```

---

## 2. `VISION_CHUNK_PROMPT`

### 是否保留

保留。

### 职责

把关键帧转成可靠画面事实。

### 不做什么

```text
不判断最终高光。
不决定是否成片。
不打复杂分数。
不推断画面没有出现的信息。
```

### 推荐输出

```json
{
  "scene_type": "",
  "visual_summary": "",
  "screen_text": [],
  "visible_people": [],
  "location_clues": [],
  "footage_type": "",
  "asr_visual_consistency": "",
  "warnings": []
}
```

### 字段解释

| 字段                       | 含义              | 用途                |
| ------------------------ | --------------- | ----------------- |
| `scene_type`             | 画面类型            | 给后续判断是现场、口播、资料、图表 |
| `visual_summary`         | 一句话画面描述         | 给候选片段和配音文案使用      |
| `screen_text`            | 画面文字            | 新闻事实辅助            |
| `visible_people`         | 可见人物或身份线索       | 辅助判断人物讲话/采访       |
| `location_clues`         | 地点线索            | 辅助新闻地点判断          |
| `footage_type`           | 现场/资料/口播/B-roll | 防止误把资料当现场         |
| `asr_visual_consistency` | ASR 与画面是否一致     | 防止画面和文案两张皮        |
| `warnings`               | 风险提示            | 资料画面、画面不清、无法确认等   |

删除：

```text
visual_value_score
hook_score
event_clues
risk_tags
notes
```

这些容易变成噪音。

---

## 3. `VIDEO_UNDERSTANDING_PROMPT`

### 是否保留

保留。

### 职责

理解整条视频的新闻背景。

### 不做什么

```text
不选片。
不判断成片数量。
不规划短视频。
不写配音文案。
```

### 推荐输出

```json
{
  "main_topic": "",
  "video_type": "",
  "summary": "",
  "key_facts": [],
  "people": [],
  "locations": []
}
```

### 字段解释

| 字段           | 含义        | 为什么保留                |
| ------------ | --------- | -------------------- |
| `main_topic` | 整条新闻主主题   | 给后续选片和重组提供主题边界       |
| `video_type` | 新闻类型      | 区分发布会、现场、连线、事故、国际政治等 |
| `summary`    | 2-3 句新闻摘要 | 给后续 prompt 建立上下文     |
| `key_facts`  | 核心事实点     | 防止后续漏掉关键信息           |
| `people`     | 重要人物      | 辅助人物表态类新闻            |
| `locations`  | 地点        | 辅助地点和现场判断            |

删除：

```text
content_structure
potential_angles
source_time_range
confidence
```

这些要么不稳定，要么和后续选片职责重叠。

## 4. `CONTENT_ANALYSIS_PROMPT`

### 是否保留

保留。

### 使用场景

AI 配音流程。

### 职责

从整条视频中找出适合 AI 配音解说的候选片段。

### 不做什么

```text
不生成最终短视频。
不决定最终 clip 顺序。
不写配音文案。
不输出时间码。
不输出时长。
不生成 clip_id。
不输出 source_id。
```

### 推荐输出

```json
{
  "main_topic": "",
  "video_news_type": "",
  "summary": "",
  "key_facts": [],
  "candidate_clips": [
    {
      "chunk_ids": [],
      "summary": "",
      "type": ""
    }
  ]
}
```

### 字段解释

| 字段                | 含义               | 用途                               |
| ----------------- | ---------------- | -------------------------------- |
| `main_topic`      | 新闻主题             | 给短视频规划和配音文案                      |
| `video_news_type` | 新闻类型             | 辅助选片标准                           |
| `summary`         | 整体摘要             | 后续规划上下文                          |
| `key_facts`       | 必须保留事实           | 后续配音必须覆盖                         |
| `chunk_ids`       | 候选片段由哪些 chunk 组成 | 代码据此计算 start/end/duration/source |
| `summary`         | 候选片段摘要           | 给短视频规划判断                         |
| `type`            | 候选类型             | 核心事实/现场证明/关键表态/影响结果等             |

### 关键改动

以前让模型输出：

```text
clip_id
start
end
duration_seconds
source_id
speech
visual
score
```

全部删。

由代码根据 `chunk_ids` 回填。

## 5. `HIGHLIGHT_DETECTION_PROMPT`

### 是否保留

保留。

### 使用场景

高光重组流程。

### 职责

从时间轴中找出适合原声重组的候选高光片段。

### 不做什么

```text
不生成最终视频。
不决定最终排序。
不输出时间码。
不输出时长。
不生成 clip_id。
不打复杂分数。
```

### 推荐输出

```json
{
  "candidate_clips": [
    {
      "chunk_ids": [],
      "summary": "",
      "type": ""
    }
  ]
}
```

### 候选选择标准

应该明确写进 prompt：

```text
优先选择：
1. 关键人物表态。
2. 现场冲突或行动。
3. 官方通报或权威回应。
4. 事件发生、升级、转折、结果。
5. 画面和声音能共同证明新闻事实的片段。

不要选择：
1. 纯重复口播。
2. 空镜头。
3. 没有新增信息的 B-roll。
4. 断句严重的半句话。
5. 需要大量上下文才能理解的碎片。
```

## 6. `SHORT_VIDEO_EDIT_PLAN_TEXT_PROMPT`

### 是否保留

保留，核心 prompt。

### 使用场景

AI 配音流程。

### 职责

从候选 clip 中决定：

```text
1. 做几条 AI 配音短视频。
2. 每条视频用哪些 clip。
3. clip 的排列顺序。
4. 每条视频的讲述重点。
5. 配音必须讲到哪些事实。
```

### 不做什么

```text
不写 narration_text。
不生成字幕。
不生成时间码。
不生成 shot_id。
不生成 short_video_id。
不输出 source_start/source_end。
不输出 duration_seconds。
不输出 title。
不输出复杂 editing_structure。
```

### 输入应该包含

```text
output_mode
max_output_videos
min_output_video_seconds
max_output_video_seconds
新闻主题
关键事实
候选 clips
每个 clip 的 clip_id、source_id、duration_seconds、summary、speech、visual、type
多源边界规则
```

### 推荐输出

```json
{
  "videos": [
    {
      "clip_ids": ["clip_001", "clip_003"],
      "讲述重点": "",
      "必须讲到": []
    }
  ]
}
```

### 规划原则

```text
1. 默认优先做一条完整新闻短视频。
2. 只有明显不同新闻事件、不同强角度、不同人物阶段，才允许多条。
3. 不要为了凑数量拆碎片。
4. 不要重复使用表达同一事实的 clip。
5. 不要选择空镜、重复口播、无新增信息片段。
6. 根据 clip 的 duration_seconds 控制总时长。
7. 不输出目标时长，代码计算视觉总时长。
```

## 7. `VOICEOVER_SCRIPT_TEXT_PROMPT`

### 是否保留

必须保留，核心 prompt。

### 使用场景

AI 配音流程。

### 职责

根据短视频规划和 shot 结构生成最终 AI 配音文案。

### 不做什么

```text
不重新选片。
不改变 shot_id。
不新增事实。
不生成剪辑计划。
不输出时间码。
```

### 输出字段保持不变

```json
{
  "scripts": [
    {
      "short_video_id": "v_001",
      "narration_text": "",
      "narration_segments": [
        {
          "shot_id": "v_001_s01",
          "text": ""
        }
      ]
    }
  ]
}
```

这个字段不建议中文化，因为 TTS、字幕、cut_plan 后续会依赖。

### 优化重点

你补充的文档应该作为这个 prompt 的主体。重点包括：事实准确、结构清楚、节奏有起伏、短句、适合字幕、和 shot 对齐、不要营销号、不要记者署名。

必须写进 prompt 的规则：

```text
1. 开头第一句必须快速点题。
2. 全文只基于输入事实。
3. 中文新闻解说口吻，克制、清楚、有信息密度。
4. 不使用“震惊”“万万没想到”“全网炸锅”等营销号表达。
5. 不写“记者某某报道”“本台消息”等署名。
6. 每句话尽量短，适合一行字幕。
7. 每个 narration_segment 必须对应一个 shot_id。
8. narration_text 必须等于所有 narration_segments 的自然合并。
9. 40 秒以上视频应包含开头、背景、核心事实、影响/冲突、当前进展。
10. 40 秒以下视频优先保留核心事件、关键细节、当前结果。
11. 结尾不要强行升华，应交代当前状态或后续关注点。
12. 根据视觉总时长控制文案字数。
```

## 8. `HIGHLIGHT_REASSEMBLY_TEXT_PROMPT`

### 是否保留

保留。

### 使用场景

高光重组流程。

### 职责

从候选 clip 中决定最终原声重组视频：

```text
1. 做几条原声重组视频。
2. 每条选哪些 clip。
3. clip 顺序是什么。
```

### 不做什么

```text
不生成 reassembly_id。
不生成 title。
不输出 source_start/source_end。
不输出 duration_seconds。
不输出 source_id。
不输出 transition_after。
不输出 excluded_clip_ids。
```

### 推荐输出

```json
{
  "videos": [
    {
      "clip_ids": ["clip_001", "clip_002"]
    }
  ]
}
```

### 规划原则

```text
1. 优先保证原声句子完整。
2. 不要从半句话切入或切出。
3. 不要把不同 source 误拼成同一连续现场。
4. 跨源组合必须有新闻逻辑。
5. 默认一条完整高光视频，不要拆碎。
6. 多条输出时必须主题或阶段明显不同。
```

# 八、最终优化原则

以后写 prompt 按这几条执行：

```text
1. 一个 prompt 只做一件事。
2. 模型只输出判断结果。
3. 代码已知的信息，不让模型输出。
4. 可以计算的信息，不让模型输出。
5. 下游不消费的字段，不让模型输出。
6. 不使用抽象缩写字段。
7. 不使用大模型不稳定评分。
8. 每个字段必须说明：含义、来源、用途、下游是否使用。
9. 公共策略尽量删，规则写进对应 prompt。
10. 所有 prompt 输出 schema 极简。
```
