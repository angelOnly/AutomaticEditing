# 凤凰新闻原声高光重组选片链路最终合并方案

> 本文档由“整体优化说明”和“细节优化方案”合并而来。  
> 合并原则：相同功能合并到同一章节；整体架构、问题定位、数据流、职责边界、字段设计、保留/删除/合并规则、错误诊断、质量检查等关键信息全部保留；重复表述合并，不做简化删减。

---

# 1. 问题定位

当前报错：

```text
reassembly_cut_plan has no available clips
```

不应该继续按“5 秒过滤”理解。5 秒只是 `reassembly_cut_plan` 末端的一个兜底规则，不是根因。

从现有代码看，当前原声高光重组链路大致是：

```text
source_analysis
→ source_aggregate
→ video_understanding
→ highlight_detection
→ highlight_reassembly_plan
→ reassembly_cut_plan
→ news_quality_gate
→ news_quality_ai_review
→ reassembly_render
```

其中：

```text
highlight_detection：
负责从时间线里找候选片段。

highlight_reassembly_plan：
再从候选片段里选择 clip_id，决定组合和排序。

reassembly_cut_plan：
把重组规划转换成最终剪辑计划。
```

这个流程看起来完整，但中间存在几个核心问题：

```text
1. highlight_detection 选的是 chunk，不是真正可剪的 ASR 事件片段。
2. 60 秒 chunk 太粗，不能直接承担“候选片段”职责。
3. candidate_filter.txt 已经存在，但当前没有真正接入工作流。
4. pipeline.py 里的 step_candidate_refine() 当前是直接跳过的。
5. 高光重组工作流里没有正式的 candidate_filter / candidate_refine 步骤。
6. 大模型和代码之间的 clip_id 契约不够稳定。
7. 模型可能影响或生成时间码，导致 source_id / 时间边界混乱。
8. 虚拟时间轴参与了候选片段和剪辑定位，容易造成源视频时间和全局时间混用。
9. reassembly_cut_plan 承担了太多兜底职责，既解析模型输出，又修正时间，又过滤短片段。
10. 失败时只能报 no available clips，不能明确指出到底断在哪一步。
```

`candidate_filter.txt` 本身已经写明职责：  
在系统生成的 `candidate_clips` 中判断哪些片段应保留，哪些相邻片段应作为同一事实链合并使用，并输出：

```json
{
  "keep_clip_ids": [],
  "merge_groups": []
}
```

但实际代码里 `step_candidate_refine()` 现在是跳过的，高光重组流程也没有把 `candidate_filter` 正式接入执行链路。

所以，这不是一个单点 bug，也不是单纯“5 秒过滤”导致的问题，而是选片链路设计不稳：

```text
候选片段生成太粗；
候选复核缺失；
clip_id 选择和候选池回查不稳定；
重组模型和剪辑计划之间缺少强契约；
失败时没有告诉用户到底断在哪一层。
```

---

# 2. 最终优化目标

目标不是继续给 `reassembly_cut_plan` 打补丁，而是重建一条稳定的、可诊断的、以 `clip_id` 为核心的选片链路。

最终要从当前链路：

```text
source_analysis
→ source_aggregate
→ video_understanding
→ highlight_detection
→ highlight_reassembly_plan
→ reassembly_cut_plan
```

优化成：

```text
source_prepare
→ source_analysis
→ source_aggregate
→ video_understanding
→ asr_event_candidate / asr_event_candidate_build
→ candidate_clip_pool_build
→ candidate_filter
→ highlight_reassembly_plan
→ reassembly_cut_plan
→ news_quality_gate
→ news_quality_ai_review
→ reassembly_render
```

如果暂时没有 `source_prepare` 独立步骤，也可以落成：

```text
source_analysis
→ source_aggregate
→ video_understanding
→ asr_event_candidate_build
→ candidate_filter
→ highlight_reassembly_plan
→ reassembly_cut_plan
→ news_quality_gate
→ news_quality_ai_review
→ reassembly_render
```

核心变化是：

```text
不要再让 60 秒 chunk 直接承担“候选片段”职责。
不要让模型反复生成时间码。
不要让 reassembly_cut_plan 负责猜测为什么没有 clips。
要建立一个稳定的 candidate_clip_pool.json。
后续所有选片、重组、剪辑都围绕 candidate_clip_pool 的 clip_id 做回查。
```

核心原则：

```text
1. ASR 事件价值优先。
2. 原声重组模式下，视觉只做辅助判断，不做主选片依据。
3. AI 配音模式下，可以保留画面强但原声弱的片段。
4. 大模型禁止输出最终剪辑时间区间。
5. 所有后续步骤只围绕稳定 clip_id 选择和回查。
6. 虚拟时间轴只用于展示、排序和上下文，不用于最终剪辑定位。
7. reassembly_cut_plan 不再猜测模型输出，而是确定性地按 clip_id 回查候选池。
8. 失败诊断必须结构化，明确是哪一步断了。
```

---

# 3. 优化后的整体架构

建议将原流程调整为：

```text
source_prepare
→ source_analysis
→ source_aggregate
→ video_understanding
→ asr_event_candidate
→ candidate_clip_pool_build
→ candidate_filter
→ highlight_reassembly_plan
→ reassembly_cut_plan
→ news_quality_gate
→ news_quality_ai_review
→ reassembly_render
```

其中：

```text
source_analysis / source_aggregate：
负责每个素材的 ASR、视觉、chunk 摘要和多源汇总。

video_understanding：
负责理解整体新闻主题、事件关系、人物、背景和主线。

asr_event_candidate / asr_event_candidate_build：
基于 ASR 文本找出有新闻价值的原声事件候选。
这个步骤不是最终成片规划，只是找“哪些声音片段值得进入候选池”。

candidate_clip_pool_build：
代码根据模型输出的 segment_id / keep / merge 回查原始 ASR 片段，补齐 clip_id、source_id、source_start、source_end、duration、speech、visual 等字段。

candidate_filter：
对候选 clip 做保留、删除、合并建议和必要排序。
它不是重新生成候选，而是复核已有候选池。

highlight_reassembly_plan：
只决定用哪些 clip_id、按什么顺序、组成几条原声高光视频。

reassembly_cut_plan：
只根据 clip_id 回查 source_id + source_start + source_end，生成确定性剪辑计划。

news_quality_gate：
本地规则质检，防止空片段、缺字段、无效拼接进入渲染。

news_quality_ai_review：
大模型做新闻表达风险审校。

reassembly_render：
按剪辑计划渲染原声重组视频。
```

最终链路要拆成四个核心层级：

```text
第一层：ASR 事件候选生成
第二层：候选片段复核 candidate_filter
第三层：高光重组只选 clip_id
第四层：剪辑计划只按 clip_id 回查，不再猜时间
```

---

# 4. 第一层：ASR 事件候选生成

## 4.1 为什么要新增这一层

现在 `highlight_detection` 是从 timeline chunk 里选候选。它的 prompt 要求模型输出 `chunk_ids` 和 `summary`，并且明确不要输出：

```text
start
end
duration_seconds
clip_id
source_id
```

这说明它本质上选的是：

```text
哪些 chunk 值得关注
```

不是：

```text
哪一段原声可以直接剪
```

这会导致候选过粗。比如一个 60 秒 chunk 里只有中间 18 秒有价值，但系统会把整个 chunk 当候选。后面再让模型选 clip，容易出现不稳定。

所以需要新增正式步骤：

```text
asr_event_candidate_build
```

它不是看画面选片，而是先看声音内容，按 ASR 事件段生成真正可剪的候选池。

---

## 4.2 ASR 事件候选生成的职责边界

这个步骤只做：

```text
从 ASR / speech 文本中识别值得保留的新闻原声事件段。
基于 ASR 文本，按 source_id 独立识别新闻事件片段。
```

不做：

```text
不决定最终成片。
不决定视频顺序。
不输出 source_start/source_end。
不输出虚拟时间。
不输出剪辑时间。
不评价复杂分数。
不做渲染决策。
不跨 source 合并成一个 clip。
```

这个步骤的核心不是让模型写复杂结构，而是让它做一个非常明确的判断：

```text
哪些 ASR 片段有新闻事件价值，值得进入候选池？
```

---

## 4.3 输入

输入来自公共分析结果：

```text
source_aggregate.json
每个 source 的 timeline_digest
每个 chunk 的 speech / visual / source_id / source_index / local_start / local_end
```

当前 `source_aggregate` 已经会把每个 source 的 chunk 汇总到统一 digest 里，而且保留：

```text
source_id
source_index
local_start
local_end
global_start
global_end
speech
visual
```

输入给模型时可以是代码准备好的 ASR 片段列表，每个输入项已经带有稳定 id 和时间，但这些时间只给模型理解，不允许模型输出。

建议输入项包括：

```text
segment_id
source_id
source_index
time_range_for_reference
speech
nearby_context
visual_summary
```

如果第一版还没有细粒度 ASR segment，可以先用 chunk 内 ASR 文本粗切，后续再优化到 ASR segment 级别。

---

## 4.4 大模型最小输出结构

你补充得对：ASR 事件候选生成不能让大模型输出很多字段。

模型只输出必要字段，其他字段由代码补齐。

最小输出建议：

```json
{
  "keep": [],
  "merge": []
}
```

或者：

```json
{
  "keep_segment_ids": [],
  "drop_segment_ids": [],
  "merge_groups": []
}
```

字段含义：

```text
keep：
保留的 ASR segment_id。

drop：
可选，明确删除的 ASR segment_id。不是必须字段。

merge：
建议合并为同一候选事件的 segment_id 组。
```

示例：

```json
{
  "keep": ["s001", "s002", "s006"],
  "merge": [
    ["s001", "s002"]
  ]
}
```

不要让模型输出：

```text
source_start
source_end
duration_seconds
clip_id
source_id
虚拟时间
分数
长解释
```

这些全部由代码回查和补齐。

---

## 4.5 代码补齐后的候选池结构

模型只输出 `keep` 和 `merge` 后，代码负责生成真正的候选池：

```text
candidate_clip_pool.json
```

每个候选片段必须包含：

```json
{
  "clip_id": "src03_evt_001",
  "source_id": "source_003",
  "source_index": 3,
  "source_start_seconds": 123.4,
  "source_end_seconds": 158.6,
  "source_start": "00:02:03.400",
  "source_end": "00:02:38.600",
  "duration_seconds": 35.2,
  "segment_ids": ["s001", "s002"],
  "asr_text": "",
  "speech": "",
  "event_summary": "",
  "event_type": "key_statement / live_scene / official_response / conflict_turning_point / result / background",
  "news_value": "high / medium / low",
  "independent": true,
  "needs_context": false,
  "context_reason": "",
  "source_chunk_ids": [],
  "visual_summary": "",
  "visual": "",
  "visual_support": "strong / medium / weak / unknown"
}
```

字段来源：

```text
clip_id：
代码生成，必须稳定。

source_id：
代码继承，必须明确。

source_index：
代码继承，用于排序和展示。

source_start_seconds / source_end_seconds：
代码根据 segment 起止计算，必须是源视频本地时间。

source_start / source_end：
代码格式化后的源视频本地时间。

duration_seconds：
代码计算。

segment_ids：
该候选 clip 对应的 ASR segment_id 列表。

asr_text / speech：
代码拼接 segment 文本。

event_summary：
可由代码轻量摘要生成，或由模型在非关键字段中补充，但不作为剪辑定位依据。

event_type：
可选，用于后续排序或展示。

news_value：
可选，用于后续排序或展示。

independent / needs_context / context_reason：
用于判断是否能独立成片，或是否需要合并。

source_chunk_ids：
回溯来源 chunk。

visual_summary / visual：
代码拼接或取邻近视觉摘要。

visual_support：
画面对原声事实的支撑程度。
```

重点是：

```text
clip_id 必须稳定。
source_id 必须明确。
时间必须是源视频本地时间。
不要用虚拟时间作为剪辑主时间。
大部分字段不是模型输出，而是代码从输入 segment 里回查。
```

这样模型不会再制造时间错误。

---

## 4.6 时间粒度

不要再直接使用 60 秒 chunk 作为候选片段。

应该从 ASR 句段或 ASR digest 中构造候选：

```text
最短建议：8 秒
常规建议：12-45 秒
较长同期声：45-60 秒可以允许，但必须有完整表态或现场过程
```

如果 ASR 是按 chunk 摘要压缩过的，第一版可以先用 chunk 内 ASR 文本粗切。后续再优化到 ASR segment 级别。

这样后续不再依赖模型临时写时间码，也不再依赖 60 秒 chunk 被整体选中。从这一层开始，系统就有了真正可剪的候选片段。

# 5. ASR 事件候选保留规则

ASR 事件候选的规则必须明确，否则模型会乱保留、乱删除。

判断优先级：

```text
ASR 事实价值
> 原声完整性
> 独立成片性
> 新闻推进作用
> 视觉支撑
> 画面吸引力
```

原声重组模式尤其要优先看：

```text
有明确新闻事实；
有关键人物表态；
有事件进展、转折、结果、回应；
有现场同期声价值；
能单独听懂；
不是半句话；
不是重复背景；
不是纯空镜或无信息口播。
```

---

## 5.1 应该保留的片段

### 1. 核心事件发生

保留描述事件发生、升级、转折、结果的片段。

例如：

```text
发生了什么；
谁做了什么；
哪里发生；
造成什么后果；
事件进入什么新阶段。
```

### 2. 关键人物表态

保留人物明确、观点明确、对新闻推进有价值的表态。

包括：

```text
政府官员表态；
当事人回应；
专家解释核心原因；
现场记者说明最新进展；
主持人概括核心事实。
```

### 3. 官方通报 / 权威信息

保留官方、机构、警方、法院、军方、医院、企业、国际组织等发布的信息。

尤其是：

```text
数字；
时间；
地点；
结果；
责任；
下一步安排；
政策变化。
```

### 4. 冲突与分歧

保留能体现冲突、争议、分歧、矛盾升级的片段。

例如：

```text
双方说法不同；
谈判卡点；
抗议原因；
事故责任争议；
国际关系紧张点。
```

### 5. 现场证据型原声

保留现场声音能直接支撑新闻事实的片段。

例如：

```text
记者在现场描述；
现场群众反应；
采访对象讲述经历；
发布会现场回答；
突发事件现场同期声。
```

### 6. 结果和影响

保留说明后果、影响、下一步的片段。

例如：

```text
造成多少人受影响；
政策会如何执行；
事件对地区局势的影响；
后续调查或救援安排。
```

### 7. 能独立听懂的完整表达

原声重组尤其要保留：

```text
开头清楚；
句子完整；
主谓宾明确；
不用强依赖上一句也能理解；
不是半句话。
```

---

## 5.2 不应该保留的片段

### 1. 只有背景，没有新增信息

例如：

```text
泛泛介绍；
重复历史背景；
没有新事实的铺垫；
主持人重复上一段内容。
```

### 2. 只有画面冲击，原声没有信息

原声高光重组不能只因为画面好看就保留。

例如：

```text
空镜；
慢镜头；
现场 B-roll；
音乐铺垫；
无人声画面；
只有环境声但没有新闻事实。
```

这类片段可以给 AI 配音模式用，但不适合作为原声高光核心。

### 3. 半句话 / 断句严重

例如：

```text
“所以我们认为……”
“这个问题其实……”
“然后他就……”
```

没有上下文听不懂，删除或合并，不单独保留。

### 4. 重复信息

如果多个片段都在说同一事实，只保留：

```text
表达最完整的；
声音最清楚的；
画面最支撑的；
人物最权威的。
```

### 5. 声画明显不匹配

如果 ASR 是某个事件，但画面完全是无关资料画面，原声重组模式下应谨慎保留。

### 6. 纯串场话术

例如：

```text
“来看下一条新闻”
“稍后继续关注”
“我们再来看”
“接下来把时间交给……”
```

通常不保留。

### 7. 太依赖上下文

如果单独听不懂，但与相邻片段合并后能听懂，应进入 `merge`，不要单独 keep。

---

# 6. ASR 事件候选的合并规则

`merge` 的作用是解决“单句太碎，但合起来是完整事件”的问题。

---

## 6.1 应该合并的情况

```text
同一 source_id；
时间相邻；
表达同一个事实链；
前一句是背景，后一句是结果；
前一句提出问题，后一句给出回答；
单独听不完整，合并后完整。
```

例如：

```text
s001：这次会谈的核心焦点是停火条件。
s002：双方目前仍在释放人员名单上存在分歧。
```

可以合并。

---

## 6.2 不应该合并的情况

```text
不同 source_id 被当成同一句话延续；
不同主题硬拼；
只是关键词相同但事实不同；
一个是主持人口播，一个是无关现场；
时间相距太远；
合并后超过合理原声长度。
```

尤其是多源场景：

```text
不同 source_id 可以组合成一条视频，
但不要在 ASR 事件候选阶段合并成同一个 clip。
```

跨 source 组合应该留给 `highlight_reassembly_plan` 做排序，而不是在候选生成阶段合并。

---

# 7. 第二层：正式接入 candidate_filter

ASR 事件候选生成之后，接入现有 `candidate_filter.txt` 的职责。

这里要注意：

```text
candidate_filter 不是重新生成候选，而是复核已有候选。
```

它输入的是第一层生成并由代码补齐后的：

```text
candidate_clip_pool.json
```

输出用于生成：

```text
candidate_filter.json
candidate_clip_pool_filtered.json
```

---

## 7.1 candidate_filter 的输入

输入应该是代码补齐后的候选池，每个 clip 给模型这些信息：

```text
clip_id
source_id
source_index
duration_seconds
asr_text / speech
event_summary / summary
event_type
visual_summary / visual
visual_support
independent
needs_context
production_mode
main_topic
video summary
```

这与现有 `candidate_filter.txt` 的设计一致：  
它要求输入中已有 `candidate_clips`，每个 candidate_clip 包含：

```text
clip_id
source_id
duration_seconds
speech
visual
summary
```

不要让模型输出时间。

---

## 7.2 candidate_filter 的最小输出

考虑到当前使用的模型结构化能力一般，默认建议保持极简输出：

```json
{
  "keep_clip_ids": [],
  "merge_groups": []
}
```

不建议一开始强制模型输出太多字段，因为输出越复杂越容易错。

如果需要增强诊断，可以扩展为可选结构：

```json
{
  "keep_clip_ids": [],
  "drop_clip_ids": [],
  "merge_groups": [
    {
      "clip_ids": [],
      "reason": "",
      "merged_story_type": "same_fact_chain"
    }
  ],
  "ranked_clip_ids": [],
  "diagnostics": {
    "strong_count": 0,
    "weak_count": 0,
    "main_drop_reasons": []
  }
}
```

建议落地策略：

```text
默认强制字段：
keep_clip_ids
merge_groups

可选诊断字段：
drop_clip_ids
ranked_clip_ids
diagnostics
reason
merged_story_type
```

如果模型输出可选字段失败，不影响主流程。

---

## 7.3 candidate_filter 的职责

在 `highlight_reassembly` 模式下，它只判断：

```text
这个 clip 是否适合原声重组？
是否原声完整？
是否有明确新闻事实？
是否可以独立听懂？
是否需要和相邻 clip 合并？
是否只是弱背景/空镜/B-roll？
是否有重复信息？
是否声画基本匹配？
```

它不判断：

```text
最终成片顺序；
最终输出几条视频；
最终标题；
最终剪辑时间。
```

---

## 7.4 highlight_reassembly 模式下的判断逻辑

原声重组模式必须更强调原声价值：

```text
原声完整；
单独听得懂；
有新闻事实；
不是纯解说背景；
不是重复口播；
声画基本匹配；
资料画面不能作为核心原声高光。
```

---

## 7.5 ai_voiceover 模式下的判断逻辑

AI 配音模式可以放宽：

```text
画面强但原声弱的片段可以保留；
因为后续会由 AI 配音解释事实。
```

这个区分在现有 prompt 里已经有雏形：  
AI 配音模式可以保留画面强但原声弱的片段，原声重组模式必须优先保留原声完整、信息价值明确的片段。

---

## 7.6 candidate_filter 的输出用途

`candidate_filter` 输出后，代码生成：

```text
candidate_clip_pool_filtered.json
```

生成逻辑：

```text
只保留 keep_clip_ids 对应的 clips；
如果有 ranked_clip_ids，则按 ranked_clip_ids 排序；
如果没有 ranked_clip_ids，则保持原始候选顺序或按 news_value / source_index / source_start 排序；
如果有 merge_groups，代码可以生成派生字段 story_group_id / merge_group_id；
不要马上合并真实时间，避免跨 source 误合并。
```

# 8. 第三层：highlight_reassembly_plan 只负责组片

当前 `highlight_reassembly_text.txt` 的方向是对的：  
模型只需要决定每条视频使用哪些 clip，以及 clip 的排列顺序。

优化后，`highlight_reassembly_plan` 不再负责判断“哪些片段可剪”，它只负责：

```text
从 filtered candidate pool 里选哪些 clip；
按什么顺序；
组成几条原声高光视频；
每条视频的主题是什么。
```

---

## 8.1 输入

输入 `candidate_filter` 后的候选池：

```text
clip_id
source_id
source_index
duration_seconds
summary / event_summary
speech / asr_text
visual / visual_summary
visual_support
independent
needs_context
story_group_id / merge_group_id
```

再加：

```text
主主题
整体摘要
目标时长
最大 clip 数
output_mode
production_mode
video_understanding.json
```

---

## 8.2 输出

建议核心输出仍然只包含 `clip_id` 顺序和分组：

```json
{
  "output_videos": [
    {
      "reassembly_id": "hr_001",
      "title": "",
      "storyline": "",
      "clip_ids": ["src02_evt_001", "src03_evt_002"],
      "estimated_duration_seconds": 52.4,
      "reason": ""
    }
  ]
}
```

如果要进一步极简，也可以只输出：

```json
{
  "output_videos": [
    {
      "clip_ids": ["src01_evt_001", "src03_evt_002"]
    }
  ]
}
```

或者：

```json
[
  {
    "clip_ids": ["src01_evt_001", "src03_evt_002"]
  }
]
```

不让模型输出：

```text
source_start
source_end
duration_seconds
source_id
虚拟时间
```

这些都由代码从候选池回查。

---

## 8.3 组片规则

原声高光重组应该按这个优先级：

```text
同一新闻主线优先做成一条；
不同主题才拆多条；
不要为了凑时长加入弱片段；
不要把不同 source 的半句话当成连续原声；
同一 source 的连续事实链可以相邻排列；
跨 source 可以做信息递进，例如背景 → 现场 → 回应 → 结果；
跨 source 时必须是信息递进，不是硬拼半句话；
优先核心事件，再现场证据，再关键回应，再影响/结果；
每条视频都应该能让观众听懂发生了什么。
```

# 9. 第四层：reassembly_cut_plan 确定性回查

## 9.1 当前问题

当前 `reassembly_cut_plan` 会解析模型输出里的多种结构：

```text
selected_clips
clips
clip_sequence
segments
```

然后再做：

```text
时间判断；
source 边界归一化；
短片段过滤；
缺字段兜底；
模型输出修复。
```

这一步职责太重了。它既在做剪辑计划，又在补救模型输出，还在做边界判断。最后失败时只能给出笼统的：

```text
reassembly_cut_plan has no available clips
```

---

## 9.2 优化后职责

优化后，`reassembly_cut_plan` 只做三件事：

```text
读取 highlight_reassembly_plan 的 clip_ids；
读取 candidate_clip_pool_filtered；
用 clip_id 回查 source_id + source_start + source_end；
生成最终剪辑 clips。
```

它不再相信模型输出的时间码，也不再解析模型写出的 `source_start/source_end`。

---

## 9.3 成功条件

每个进入剪辑计划的 clip 必须满足：

```text
clip_id 存在；
source_id 存在；
source_start/source_end 存在；
source_start_seconds/source_end_seconds 存在；
source_end > source_start；
duration_seconds > 0；
源文件存在；
keep_original_audio 明确；
```

最短时长规则可以保留，但不应该作为首要失败解释。

---

## 9.4 输出结构

最终 `reassembly_cut_plan.json` 里的 clips 应该来自候选池：

```json
{
  "output_videos": [
    {
      "reassembly_id": "hr_001",
      "title": "",
      "clips": [
        {
          "clip_id": "hr_001_001",
          "source_clip_id": "src03_evt_001",
          "source_id": "source_003",
          "source_start": "00:02:03.400",
          "source_end": "00:02:38.600",
          "source_start_seconds": 123.4,
          "source_end_seconds": 158.6,
          "duration_seconds": 35.2,
          "target_start": "00:00:00.000",
          "keep_original_audio": true,
          "original_audio_volume": 1.0,
          "crop_mode": "original"
        }
      ]
    }
  ]
}
```

# 10. 失败诊断必须结构化

不要再只报：

```text
reassembly_cut_plan has no available clips
```

应该拆成明确错误类型。

---

## 10.1 候选池为空

```json
{
  "error_type": "candidate_pool_empty",
  "source_chunk_count": 24,
  "reason": "ASR 事件候选生成没有找到可用原声片段",
  "suggestion": "降低候选事件阈值，或检查 ASR 文本质量"
}
```

含义：

```text
ASR 事件候选池为空。
说明 ASR 里没有找到明确新闻事件，建议检查 ASR 或放宽 ASR 事件候选规则。
```

---

## 10.2 candidate_filter 后为空

```json
{
  "error_type": "candidate_filter_empty",
  "candidate_pool_count": 10,
  "keep_clip_ids": [],
  "main_drop_reasons": ["原声不完整", "上下文缺失"],
  "suggestion": "放宽 candidate_filter，或允许保留 medium 质量片段"
}
```

含义：

```text
候选复核后没有保留任何 clip。
说明 candidate_filter 认为候选质量都不适合原声重组。
```

---

## 10.3 重组规划为空

```json
{
  "error_type": "plan_empty",
  "candidate_pool_count": 12,
  "filtered_pool_count": 8,
  "reason": "高光重组规划没有选择任何 clip_id",
  "suggestion": "重跑 highlight_reassembly_plan，或检查规划 prompt 是否过于严格"
}
```

含义：

```text
候选池有内容，但模型没有选。
```

---

## 10.4 模型选择了不存在的 clip_id

```json
{
  "error_type": "clip_id_not_found",
  "candidate_pool_count": 12,
  "filtered_pool_count": 8,
  "planned_clip_ids": ["clip_001", "clip_002"],
  "matched_clip_ids": [],
  "missing_clip_ids": ["clip_001", "clip_002"],
  "invalid_clips": [],
  "suggestion": "重跑高光重组规划，或检查 candidate_filter 输出和候选池映射"
}
```

含义：

```text
模型选择了不存在的 clip_id。
说明规划输出和候选池不匹配，属于模型输出格式或代码映射问题。
```

## 10.5 候选 clip 时间无效

```json
{
  "error_type": "clip_time_invalid",

    {
      "clip_id": "src03_evt_001",
      "reason": "source_end <= source_start"
    }
  ],

}
```

含义：

```text
候选池里的 clip 时间无效。
应该回查 ASR 事件候选构造。
```

## 10.6 所有 clip 被剪辑规则过滤

```json
{
  "error_type": "all_clips_filtered",
  "candidate_pool_count": 8,
  "planned_clip_ids": ["src01_evt_001", "src02_evt_003"],
  "filtered_reason": "所有片段低于最短时长或源文件不可用",
  "suggestion": "检查最短时长规则、源文件路径、候选池时间字段"
}
```

含义：

```text
所有 clip 被剪辑规则过滤。
这时才应该考虑 5 秒过滤、源文件缺失、duration 为 0 等末端规则。
```

# 11. 虚拟时间轴处理原则

你补充的“禁止模型输出时间区间”非常关键。

最终原则：

```text
虚拟时间轴可以存在，但不能让模型输出，也不能作为最终剪辑主依据。
```

---

## 11.1 虚拟时间轴可以用于

```text
跨素材排序；
展示整体素材结构；
展示全局时间线；
帮助 video_understanding 理解多源关系；
帮助模型知道素材先后顺序；
判断素材之间的大致上下文。
```

---

## 11.2 虚拟时间轴禁止用于

```text
模型输出 source_start/source_end；
模型输出 start/end；
模型输出 duration；
剪辑计划直接使用虚拟时间；
reassembly_cut_plan 边界归一化主逻辑；
跨 source 边界自动切片作为主逻辑。
```

---

## 11.3 最终剪辑定位必须使用

```text
source_id
source_start_seconds
source_end_seconds
source_start
source_end
```

这几个字段必须由代码从候选池回查得到，不能来自模型。

这样即使虚拟时间错了，也不会影响剪辑。

# 12. news_quality_gate 必须补齐

当前流程中有：

```text
news_quality_gate
news_quality_ai_review
```

但 `PipelineRunner.run()` 是通过：

```python
getattr(self, f"step_{step}")
```

找对应方法执行。

如果没有 `step_news_quality_gate()`，即使前面 `reassembly_cut_plan` 成功，后面也会中断。

所以这里有两个选择：

```text
方案 A：实现 step_news_quality_gate，做本地规则检查。
方案 B：暂时从 workflow 里移除 news_quality_gate，只保留 news_quality_ai_review 或直接跳过。
```

更推荐方案 A。

---

## 12.1 news_quality_gate 的职责

`news_quality_gate` 不是大模型步骤，应该是轻量、本地、稳定、可解释的规则检查。

检查内容：

```text
是否有 output_videos；
每条视频是否有 clips；
每个 clip 是否有 source_id；
每个 clip 是否有 source_start/source_end；
每个 clip 是否有 source_start_seconds/source_end_seconds；
总时长是否过短；
是否存在空音频；
是否存在明显跨 source 半句话拼接；
是否存在全部 clip 都是弱信息背景；
是否存在所有 clip 都来自弱视觉/弱原声；
是否有重复 clip；
是否存在源文件缺失；
是否存在 source_end <= source_start；
是否存在 duration_seconds <= 0。
```

通过后再进入：

```text
news_quality_ai_review
```

---

## 12.2 news_quality_gate 输出

建议输出：

```json
{
  "ok": true,
  "block_render": false,
  "issues": [],
  "warnings": [],
  "stats": {
    "output_video_count": 1,
    "clip_count": 3,
    "total_duration_seconds": 55.2
  }
}
```

如果失败：

```json
{
  "ok": false,
  "block_render": true,
  "issues": [
    {
      "type": "missing_source_time",
      "clip_id": "hr_001_001",
      "message": "clip 缺少 source_start/source_end"
    }
  ],
  "suggestion": "回查 reassembly_cut_plan 或 candidate_clip_pool_filtered"
}
```

# 15. 具体优化点清单

## 15.1 选片策略优化

从：

```text
chunk 级别粗选
```

改成：

```text
ASR 事件段生成候选
```

判断优先级：

```text
ASR 事实价值
> 原声完整性
> 独立成片性
> 新闻推进作用
> 视觉支撑
> 画面吸引力
```

---

## 15.2 数据结构优化

从：

```text
模型输出 chunk_ids / clip_ids，代码临时补时间
```

改成：

```text
candidate_clip_pool 固化 clip_id + source_id + source_start + source_end
```

---

## 15.3 模型职责优化

从：

```text
模型既选片，又可能影响时间
```

改成：

```text
模型只判断保留、排序、组合，不写最终剪辑时间
```

模型可以做：

```text
判断哪些 segment 保留；
```

```text
输出最终 source_start/source_end；
输出最终 duration；

替代码修复时间边界。
```

从：

```text
reassembly_cut_plan 负责解析模型输出、修时间、过滤、报错
```

改成：

```text
reassembly_cut_plan 只按 clip_id 回查候选池并生成计划
```

## 15.5 错误诊断优化

```text
reassembly_cut_plan has no available clips
```

```text
candidate_pool_empty：

candidate_filter_empty：
候选复核后没有保留任何 clip。

plan_empty：
高光重组规划没有选择 clip_id。

clip_id_not_found：

clip_time_invalid：
候选池里的 clip 时间无效。

all_clips_filtered：

源文件缺失或路径不可用。

本地质量检查未通过。
```

每种错误都给中文原因和建议重跑步骤。

# 16. no available clips 以后应该怎么变

以后不应该再出现笼统的：

```text
reassembly_cut_plan has no available clips
```

而应该变成：

```text
没有生成 ASR 事件候选：
说明 ASR 里没有找到明确新闻事件，建议检查 ASR 或放宽 ASR 事件候选规则。

候选复核后为空：
说明 candidate_filter 认为候选质量都不适合原声重组，建议放宽复核规则或允许 medium 片段。

高光重组规划没有选择 clip：
说明候选池有内容，但模型没有选，建议重跑重组规划。

模型选择的 clip_id 不存在：
说明规划输出和候选池不匹配，属于模型输出格式或代码映射问题。

候选 clip 时间无效：
说明候选池构造有问题，应该回查 ASR 事件候选构造。

所有 clip 被末端规则过滤：
说明可能是最短时长、源文件缺失、duration 为 0 或时间边界无效。
```

这才是根治。

---

# 17. 为什么这是根本方案

这个方案解决的是选片链路的结构问题：

```text
谁生成候选？
谁复核候选？
谁决定组合？
谁负责剪辑定位？
失败时怎么定位？
```

而不是继续在末端加兼容逻辑。

改完后，`no available clips` 这种错误不应该再作为主错误出现。即使失败，也会变成明确原因：

```text
ASR 没有找到核心事件片段；
candidate_filter 把所有候选删掉；
highlight_reassembly_plan 选择了不存在的 clip_id；
候选片段缺少 source_start/source_end；
质量检查发现重组视频不可成片。
```

---

# 18. 最终结论

最终方案不是简单“修 no clips”，而是重建选片主链路：

```text
ASR 事件候选生成
→ candidate_clip_pool_build 代码补齐稳定候选池
→ candidate_filter 复核
→ highlight_reassembly_plan 只选 clip_id
→ reassembly_cut_plan 只回查 clip_id
→ news_quality_gate 本地质检
→ news_quality_ai_review 风险审校
→ reassembly_render
```

大模型只做判断，不输出时间。

代码负责生成和维护稳定候选池。

虚拟时间轴只做参考，不参与最终剪辑定位。

这样才能从根本上解决：

```text
模型选了但代码找不到；
虚拟时间和源时间混用；
候选片段太粗；
candidate_filter 没生效；
reassembly_cut_plan 只能报 no available clips；
UI 无法告诉用户真正原因。
```

这个结构稳定后，后续再优化 prompt、排序、时长、UI 错误提示，才会有基础。
