# 多源任务启动/预览修复 + 多结果输出放开：合并开发执行说明

> 适用仓库：`angelOnly/AutomaticEditing`  
> 建议把本文档作为 Codex 的主执行文档。  
> 原两份文档可以作为背景材料，但实际改代码时以本文档的“合并原则、冲突处理、执行顺序”为准。

---

## 1. 为什么建议合并

这两份文档目标不同，但会修改同一批核心文件：

- `web_static/index.html`
- `web_static/app.js`
- `web_app.py`
- `newsclip_agent/pipeline.py`
- `newsclip_agent/prompts.py`
- `config.toml`

如果分别让 Codex 按两份文档独立开发，容易出现后改覆盖先改的问题，例如：

- 第一份文档要求 `app.js` 的步骤列表新增 `source_prepare`，第二份文档也要改步骤/参数逻辑，如果没有合并，可能会把 `source_prepare` 改丢。
- 第一份文档要求 `/api/run` 多源任务只创建 job，把下载/FFmpeg 移到子进程；第二份文档要求 `/api/run` 新增 `output_mode`、`max_output_videos` 并参与去重。如果不合并，可能出现多源任务去重没有区分“单条/多条结果”。
- 第一份文档要求 `_build_run_command()` 支持 `run_multisource_pipeline.py`；第二份文档要求 `_build_run_command()` 传 `--output-mode`。这两个必须写在同一个命令构造函数里。
- 第一份文档要求 `afterJobStarted()` 处理提交中、排队中、复用结果；第二份文档要求多结果输出的成片列表正确展示。两者都影响任务启动和结果刷新。

结论：**建议合并执行，不建议把两份文档直接同时发给 Codex 让它自由决定。**

---

## 2. 合并后的总体目标

一次开发同时完成：

1. 多源任务点击“开始分析”后立即创建 job，不再在 `/api/run` 里同步下载、转码、拼接。
2. 多源准备进入子进程执行，日志能实时显示 `source_prepare` 进度。
3. 相同多源素材、相同顺序、相同生产模式、相同输出模式、相同关键参数能正确去重。
4. 原片预览支持：拼接原片 + 每个原始素材预览。
5. Web 端支持选择：生成一个视频 / 生成多个视频。
6. AI 解说和视频重组都支持多条结果。
7. 多源 + 多结果输出时，避免重复片段、跨源边界误剪、任务复用错误、成片列表缺失等问题。

## 3. 关键冲突点与统一处理方案

### 3.1 `web_app.py`：`RunRequest` 字段合并

最终 `RunRequest` 需要同时包含多源字段和多结果字段。

保留已有字段：

```python
input_video: str | None = None
input_videos: list[str] = Field(default_factory=list)
remote_video: dict[str, Any] | None = None
remote_videos: list[dict[str, Any]] = Field(default_factory=list)
source_items: list[dict[str, Any]] = Field(default_factory=list)
force_remote_download: bool = False
```

新增通用输出字段：

```python
output_mode: str = "single"          # single / multiple
max_output_videos: int = 1            # single=1, multiple 默认 5 或 6
min_output_video_seconds: int = 30
max_output_video_seconds: int = 90
```

保留视频重组字段：

```python
reassembly_output_mode: str = "single"
reassembly_sort_mode: str = "editorial"
reassembly_target_seconds: int | None = None
reassembly_max_clip_count: int = 8
reassembly_export_individual_clips: bool = False
```

统一规则：

```python
if req.output_mode not in {"single", "multiple"}:
    req.output_mode = "single"

if req.output_mode == "single":
    req.max_output_videos = 1
else:
    req.max_output_videos = max(2, min(int(req.max_output_videos or 5), 10))

if req.production_mode == "highlight_reassembly":
    req.reassembly_output_mode = "multiple" if req.output_mode == "multiple" else "single"
```

### 3.2 `/api/run`：多源准备与多结果去重要合并

第一份文档要求多源任务不要在 `/api/run` 里同步执行 `build_multi_source_video()`。

第二份文档要求任务 fingerprint 区分 `output_mode`。

最终方案：

1. `/api/run` 收到请求。
2. 读取原始 `source_items`，只做轻量校验。
3. 计算 fingerprint，必须包含：
   - 源素材列表
   - 源素材顺序
   - 本地素材 path / size / mtime
   - 远程素材 id / guid / name / record_station / download_url
   - `production_mode`
   - `output_mode`
   - `max_output_videos`
   - `aspect_ratio`
   - `chunk_seconds`
   - `frame_interval`
   - `target_duration_seconds`
   - `reassembly_target_seconds`
   - `reassembly_max_clip_count`
4. 如果相同任务运行中，直接返回已有 job。
5. 如果相同任务已完成，直接返回已完成任务。
6. 多源任务只写 `input/source_request.json`，立即创建 job。
7. 子进程读取 `source_request.json` 后再下载远程素材、标准化、拼接。

伪代码：

```python
@app.post("/api/run")
def run_pipeline(req: RunRequest) -> dict[str, Any]:
    _normalize_output_options(req)
    _prepare_mode_switched_run(req)

    raw_source_items = _collect_source_items(req)
    is_multi_source = len(raw_source_items) > 1

    if is_multi_source:
        fingerprint = _source_request_fingerprint(req)
        task_id = req.task_id.strip() if req.task_id else _make_task_id_from_fingerprint(
            _display_source_request_name(req),
            req.production_mode,
            fingerprint,
        )
        task_dir = ensure_dir(OUTPUTS_DIR / task_id)

        existing_job = _find_active_job_by_task_id(task_id)
        if existing_job and not (req.rerun or req.rerun_from):
            return {**_public_job(existing_job), "deduplicated": True, "message": "相同多源任务正在处理中，已切换到现有任务。"}

        manifest = read_json(task_dir / "manifest.json", {})
        if not (req.rerun or req.rerun_from) and _is_task_already_completed(manifest, req.production_mode):
            return {"job_id": "", "task_id": task_id, "status": "success", "deduplicated": True, "message": "相同多源任务已完成，直接复用结果。"}

        source_request_path = task_dir / "input" / "source_request.json"
        ensure_dir(source_request_path.parent)
        write_json(source_request_path, {
            "source_items": raw_source_items,
            "force_remote_download": req.force_remote_download,
            "output_mode": req.output_mode,
            "max_output_videos": req.max_output_videos,
            "aspect_ratio": req.aspect_ratio,
            "created_at": datetime.now().isoformat(timespec="seconds"),
        })

        input_path = None
        source_manifest_path = None
    else:
        # 保持单源现有逻辑，但 fingerprint 也要加入 output_mode/max_output_videos
        ...

    cmd = _build_run_command(
        req,
        task_id,
        input_path=input_path,
        source_manifest_path=source_manifest_path,
        source_request_path=source_request_path if is_multi_source else None,
    )
```

### 3.3 `_build_run_command()`：同时支持多源子进程和输出模式

最终 `_build_run_command()` 必须同时完成：

- 单源任务：调用 `run_pipeline.py`
- 多源任务：调用 `run_multisource_pipeline.py`
- 两种任务都要传 `--output-mode` / `--max-output-videos`
- 视频重组继续传 `--reassembly-output-mode`

伪代码：

```python
def _build_run_command(req, task_id, input_path=None, source_manifest_path=None, source_request_path=None):
    if source_request_path:
        cmd = [
            sys.executable, "-u", str(MULTI_SOURCE_RUNNER),
            "--source-request", str(source_request_path),
            "--task-id", task_id,
            "--aspect-ratio", req.aspect_ratio,
        ]
    else:
        cmd = [
            sys.executable, "-u", str(RUNNER),
            "--task-id", task_id,
        ]

    cmd.extend([
        "--chunk-seconds", str(req.chunk_seconds),
        "--frame-interval", str(req.frame_interval),
        "--aspect-ratio", req.aspect_ratio,
        "--target-duration", str(req.target_duration_seconds),
        "--audio-policy", req.audio_policy,
        "--production-mode", req.production_mode,
        "--output-mode", req.output_mode,
        "--max-output-videos", str(req.max_output_videos),
    ])

    if req.production_mode == "highlight_reassembly":
        cmd.extend(["--reassembly-output-mode", req.reassembly_output_mode])
        cmd.extend(["--reassembly-sort-mode", req.reassembly_sort_mode])
        cmd.extend(["--reassembly-max-clip-count", str(req.reassembly_max_clip_count)])

    if input_path:
        cmd.extend(["--input", str(input_path)])
    if source_manifest_path:
        cmd.extend(["--source-manifest", str(source_manifest_path)])

    # 继续保留 rerun / rerun_from / skip_tts / skip_render 等现有参数
    return cmd
```

### 3.4 `run_multisource_pipeline.py`：要透传输出模式

`run_multisource_pipeline.py` 使用 `parse_known_args()` 时，未知参数要原样透传给 `pipeline.main()`。

因此 Web 传入的：

```text
--output-mode multiple
--max-output-videos 5
--reassembly-output-mode multiple
```

必须继续传给 `newsclip_agent.pipeline.main([...])`。

核心逻辑：

```python
args, passthrough = parser.parse_known_args()
...
pipeline_args = [
    "--task-id", args.task_id,
    "--input", str(built["input_video"]),
    "--source-manifest", str(built["source_manifest"]),
    *passthrough,
]
return pipeline_main(pipeline_args)
```

### 3.6 `afterJobStarted()`：同时处理任务复用和多结果刷新

最终逻辑：

- 如果 `job.status=success` 且 `job.job_id` 为空：说明复用已完成任务，必须主动加载 manifest、成片列表、文件树。
- 如果 `job.deduplicated=true` 且有 `job_id`：说明切换到运行中任务，显示提示但不要只弹窗。
- 多结果输出时，`draftList` 已支持遍历多个成片，保留即可。

伪代码：

```javascript
async function afterJobStarted(job) {
  state.activeJob = job.job_id || null;
  state.selectedTask = job.task_id;
  updateJobMessage(job.message || "");

  if (!job.job_id && job.status === "success") {
    $("metricJob").textContent = "已完成";
    await loadManifest(job.task_id).catch(() => {});
    await loadLatestDraft(job.task_id).catch(() => {});
    await loadTree().catch(() => {});
    return;
  }

  if (job.deduplicated) {
    $("logViewer").textContent = job.message || "已切换到现有任务。";
  } else {
    updateProgress(0, STEPS.length, 0, 0, 0);
    $("metricCurrentStep").textContent = stepLabel(STEPS[0]);
    $("logViewer").textContent = "任务已提交，等待日志输出...";
  }

  if (state.activeJob) startJobPolling();
  refreshActiveTaskSnapshot(job.task_id);
  if (state.activeJob) refreshJobAndLog();
}
```

### 3.7 `pipeline.py`：不要把 `source_prepare` 加入真实步骤顺序

为避免影响现有缓存和步骤依赖，第一阶段不要把 `source_prepare` 加入 `AI_VOICEOVER_STEP_ORDER` / `HIGHLIGHT_REASSEMBLY_STEP_ORDER` 的真实 pipeline 执行顺序。

`source_prepare` 状态由 `run_multisource_pipeline.py` 写入 `manifest.steps.source_prepare`。

前端步骤列表可以展示 `source_prepare`。

这点以第一份文档为准。

`pipeline.py` 只需要为多结果输出增加：

```python
@dataclass
class RunOptions:
    output_mode: str = "single"
    max_output_videos: int = 1
    min_output_video_seconds: int = 30
    max_output_video_seconds: int = 90
```

`parse_args()` 增加：

```python
parser.add_argument("--output-mode", choices=["single", "multiple"], default="single")
parser.add_argument("--max-output-videos", type=int, default=1)
parser.add_argument("--min-output-video-seconds", type=int, default=30)
parser.add_argument("--max-output-video-seconds", type=int, default=90)
```

然后在 `_record_run_options()`、`_run_options_payload()`、`_run_options_payload_minimal()`、`_reassembly_options_payload()` 中写入这些字段。

### 3.8 `_normalize_short_video_split_decision()`：尊重 output_mode

单条模式：允许/强制合并为一条。

多条模式：禁止系统后处理把模型输出的多条全部合并成一条，只做质量过滤。

```python
def _normalize_short_video_split_decision(self, edit_plan: dict[str, Any]) -> dict[str, Any]:
    if not isinstance(edit_plan, dict):
        return edit_plan
    scripts = [x for x in edit_plan.get("scripts", []) if isinstance(x, dict)]
    if len(scripts) <= 1:
        return edit_plan

    if self.options.output_mode == "multiple":
        normalized = dict(edit_plan)
        max_count = max(2, int(self.options.max_output_videos or 5))
        normalized["scripts"] = scripts[:max_count]
        normalized["recommended_video_count"] = len(normalized["scripts"])
        normalized["auto_merge_applied"] = False
        normalized["output_mode_respected"] = "multiple"
        return normalized

    # single 模式才合并
    normalized = dict(edit_plan)
    normalized["recommended_video_count"] = 1
    normalized["scripts"] = [self._merge_short_video_scripts(scripts)]
    normalized["auto_merge_applied"] = True
    normalized["auto_merge_reason"] = "user_selected_single_output"
    return normalized
```

### 3.9 `prompts.py`：提示词同时理解 output_mode 和多源边界

提示词需要同时加入两类信息：

1. `run_options.output_mode` / `max_output_videos`
2. 多源任务里的 `source_videos` / `source_manifest` 边界信息

建议新增常量：

```python
MULTI_OUTPUT_PROGRAM_SPLIT_POLICY = """
多结果输出策略：
你必须读取 run_options.output_mode 和 run_options.max_output_videos。

当 output_mode == single：
- 只能输出 1 条视频。
- 选择最核心主线，做成综合片。

当 output_mode == multiple：
- 可以输出 2 到 max_output_videos 条。
- 每条必须可独立发布，信息完整，不能是 10-20 秒碎片。
- 不得为了凑数量强行拆条。
- 多条之间应尽量避免重复使用同一组 source_clip_ids。

节目类型拆条策略：
1. 时政点评类：按事件拆条；同一事件中事实和评论员观点可分别成条，但每条必须能独立理解。
2. 人物访谈类：按人物生平、人物成就、社会话题/时政观点拆条。
3. 文化人物/纪录片类：按诗词、文物、人物观点或知识点拆条；一个完整观点可拆 1-2 段。
4. 历史类：按战役节点、人物阶段、历史故事节点拆条。
"""

MULTI_SOURCE_BOUNDARY_POLICY = """
多视频源边界策略：
- 如果输入包含 source_videos 或 source_manifest，说明当前 timeline 是多个源拼接后的虚拟时间轴。
- 不要把两个源之间的自然拼接边界误判为同一镜头内的跳切。
- 每条成片可以跨源选择片段，但必须保证叙事连续，并避免从前一个源的半句话切到后一个源的半句话。
- 如果一条视频跨多个源，必须在 reason 或 split_reason 中说明跨源组合的新闻逻辑。
- 多条视频输出时，优先按事件、观点、人物阶段或历史节点分配源片段，避免所有视频都重复使用同一开头。
"""
```

把这两个策略加入：

- `SHORT_VIDEO_EDIT_PLAN_PROMPT`
- `HIGHLIGHT_REASSEMBLY_PROMPT`

并确保 `step_short_video_edit_plan()`、`step_highlight_reassembly_plan()` 的 input_data 里包含多源信息：

```python
"source_mode": self.manifest.get("source_mode", "single_source"),
"source_videos": self.manifest.get("source_videos", []),
```

## 4. 推荐执行顺序

必须按这个顺序开发，减少冲突：

1. **先改 `web_app.py` 的请求模型和去重逻辑**  
   加 `output_mode` 字段；多源 fingerprint 加入输出模式；多源任务只写 `source_request.json`。

2. **新增/调整 `run_multisource_pipeline.py`**  
   子进程执行 source_prepare，并透传 output 参数到 pipeline。

3. **改 `_build_run_command()`**  
   同时支持 `source_request_path` 和 `--output-mode` / `--max-output-videos`。

4. **改 `pipeline.py` 输出模式参数**  
   增加 `RunOptions` 字段、CLI 参数、run_options payload、后处理合并逻辑。

5. **改 `prompts.py`**  
   加多结果策略、多源边界策略、节目类型拆条策略。

6. **改前端 `index.html` / `app.js`**  
   加输出方式选择；保留 `source_prepare` 步骤；`baseRunRequest()` 传输出模式；点击立即显示提交状态；复用完成任务时自动加载结果。

7. **改原片预览接口和前端列表**  
   新增 `/api/tasks/{task_id}/source-videos`，原片按钮显示拼接原片 + 每个原始素材。

8. **最后改 `styles.css`**  
   只做样式补充，不影响逻辑。

## 5. 验收用例

### 5.1 多源 + 单条 AI 解说

- 选择 3 个视频源。
- 输出方式选择“生成一个视频”。
- 点击开始分析后 1 秒内出现 job。
- 日志显示 `source_prepare`。
- 最终 `render_outputs.json` 只有 1 个输出。
- `last_run_options.output_mode = single`。

### 5.2 多源 + 多条 AI 解说

- 选择 3-6 个视频源。
- 输出方式选择“生成多个视频”。
- 最终 `short_video_edit_plan.scripts` 有 2 条以上，最多不超过 `max_output_videos`。
- `render_outputs.json.outputs` 有多个视频。
- 多条视频不要被 `_normalize_short_video_split_decision()` 自动合并成 1 条。

### 5.3 多源 + 单条视频重组

- 输出方式选择“生成一个视频”。
- `reassembly_output_mode = single`。
- `reassembly_render_outputs.json.outputs` 只有 1 个输出。

### 5.4 多源 + 多条视频重组

- 输出方式选择“生成多个视频”。
- `reassembly_output_mode = multiple`。
- `highlight_reassembly_plan.output_videos` 有多个。
- `reassembly_render_outputs.json.outputs` 有多个。

### 5.5 去重验证

同一批素材、同一顺序、同一模式、同一输出方式：

- 重复点击不创建重复任务。
- 正在运行时切换到已有 job。
- 已完成时直接加载已有结果。

同一批素材但输出方式不同：

- 单条和多条必须是两个不同任务。

同一批素材但顺序不同：

- 必须是两个不同任务。

### 5.6 原片预览

多源任务完成后点击“原片”：

- 能看到“拼接原片”。
- 能看到“原始素材 1 / 2 / 3 ...”。
- 点击每个原始素材都能预览对应视频。

## 6. 最终给 Codex 的一句话

不要把两份原文档当作两个独立需求顺序执行。它们修改同一批文件，必须合并实现：多源任务启动/预览修复是底座，多结果输出能力是在这个底座上增加 `output_mode`。任何涉及 `web_app.py`、`app.js`、`pipeline.py` 的修改，都要同时保留 `source_prepare`、`source_request_path`、`output_mode`、`max_output_videos` 四类改动。
